# 주석 작성 스타일

이 문서는 Vitrine의 코드 주석, JSDoc과 관련 UI 문자열에 적용하는 공통 작성 규칙이다.

## 원칙

- JSDoc은 한국어로 작성하고 조회, 반환, 생성, 판단 같은 명사형으로 끝낸다. `~한다`,
  `~합니다`, `~함` 같은 문장형 종결은 사용하지 않는다.
- 마침표 종결, 가운뎃점, 대시, 화살표, 원문자와 이모지는 사용하지 않는다. 방향 표현이
  필요하면 `->` 같은 ASCII 문자를 사용한다.
- 사용자에게 노출되는 UI 문자열에도 같은 문자 규칙을 적용한다. 항목은 쉼표 또는 `1)`, `2)`
  형식으로 나열한다.

## 예시

```typescript
// 좋은 예
/** 매장 PG 트랜잭션 로그 최신순 페이지 조회 (deviceUuid 지정 시 해당 단말만) */

// 나쁜 예
/** 매장 PG 트랜잭션 로그를 조회한다. (client → server · 최신순) */
```

## 문서화 수준

- 공개 함수와 export되는 옵션 또는 설정 타입에는 한 줄 JSDoc을 작성한다.
- 스토어나 상수 객체는 객체 전체가 아니라 각 키에 한 줄 JSDoc을 작성한다.
- 여러 module이 재사용하는 공용 utility에는 `@param`을 작성한다. 사용법이 직관적이지 않으면
  `@example`을 추가한다.
- 다른 module로 옮기면 안 되는 이유, 특정 fallback이나 workaround가 필요한 이유, 순서를
  바꾸면 깨지는 이유 같은 domain 경계와 함정은 주석으로 남긴다.
- 코드만으로 의도가 분명한 내용은 주석으로 반복하지 않는다.

## 간결성

주석은 코드가 말하지 못하는 이유 하나를 한두 줄로 적는다. 다음 내용은 주석에 쓰지 않는다.

- 현재 상황, 작업 경위, 과거 시행착오 서술. 경위는 commit message, 재현 조건은 test가 소유
- 폐기한 대안의 장단점 비교. 필요하면 ADR에 기록
- 다른 파일의 주석이나 test case를 설명으로 끌어오는 참조
- 코드 흐름을 순서대로 다시 읊는 설명

세 줄 이상 설명이 필요하다고 느끼면 먼저 이름, 함수 분리, test로 드러낼 수 있는지 검토한다.

```typescript
// 좋은 예
// scanFile 캐시 entry를 공유하므로 복사해서 확장

// 나쁜 예
// scanFile이 캐시로 재사용하는 원본 entry 객체라 직접 mutate하지 않고
// controls를 얹은 새 객체로 push, 그래야 다음 scanFile 캐시 hit 때
// 이전 호출에서 계산한 controls가 새 객체에 새어 들어가지 않음
```

## 기존 위반을 발견했을 때

기존 코드에 이모지나 문장형 종결 같은 위반이 남아 있어도 새 주석에서 답습하지 않는다.
요청 범위 안의 기존 위반은 함께 정리할 수 있지만, 범위를 벗어난 대량 일괄 수정은 사용자
확인 없이 수행하지 않는다.
